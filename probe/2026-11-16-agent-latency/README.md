# Тайминги узлов запусков агента (A-3, OQ-29)

Метрика p90 шага: события `node_timing` пишутся в `agent_events` при каждом запуске
агента (узлы plan / step / check / replan / finalize / confirm, миграция 0155).
Порог по OQ-29 — **p90 шага ≤ 60 с**.

## Как снять

1. Поднять стенд на актуальном коммите, сделать живой прогон агента (режим «Агент»
   в главном чате, цель на демо-данных).
2. Снять тайминги:

   ```bash
   uv run python probe/2026-11-16-agent-latency/p90_nodes.py            # все запуски
   uv run python probe/2026-11-16-agent-latency/p90_nodes.py --run-id N # один запуск
   ```

   Скрипт читает `agent_events` по DSN (`--dsn`, по умолчанию — настройки продукта),
   печатает n / p50 / p90 / max по узлам и выходит с кодом 1, если p90 шага выше порога.
   Прямого коннекта к postgres стенда нет (listener только внутри docker-сети) — с ВМ
   можно снять дамп и посчитать офлайн, как в отчёте ниже.

## Отчёт — 16.11.2026, первый живой прогон на стенде (`b5ee879`)

Запуск №1, аккаунт owner (без профиля и собранных вакансий), GLM через серверный
провайдер. Цель «найди вакансию backend и условия въезда в Польшу» — `answered`:
план составлен, шаг поиска вызвал read_profile + search_vacancies (база пуста — агент
не выдумал данные), перестройка перенаправила на «условия въезда», второй шаг ответил
честным «данных в инструментах нет» (K-1 ещё не поднят).

| узел   |  n | p50, с | p90, с | max, с |
|--------|---:|-------:|-------:|-------:|
| check  |  3 |    0.0 |    0.0 |    0.0 |
| plan   |  1 |    6.8 |    6.8 |    6.8 |
| replan |  3 |   10.4 |   11.8 |   11.8 |
| step   |  3 |    3.9 |    7.3 |    7.3 |

**p90 шага = 7.3 с — порог 60 с (OQ-29) выполнен с запасом.** Тяжёлый узел — `replan`
(~11–12 с): вызов GLM на промпт перестройки, туда же попадает сериализация контекста.
`check` — код-эвристика, ~0 мс (модель-судья придёт с A-5 и утяжелит его).

Замечания для следующих прогонов:

- один запуск — мало для p90 как статистики; накопить выборку на серии целей после
  A-8 (субагенты) и сравнить до/после;
- замер внутри `node_timing` не включает ожидание человека (пауза `confirm` считается
  снаружи графа) — время до подтверждения отдельно не метрируется, если понадобится —
  отдельное событие.

## Отчёт — 16.11.2026, прогон с субагентами A-8 (`d3d86f8`)

Запуск №5, аккаунт owner, GLM через серверный провайдер. Засеяна одна вакансия
(smok-a8-1: Berlin, B2B, «EU residency required», €90–110k) — после прогона убрана.
Цель «оцени вакансию backend… и что известно о Германии» — `answered` за 5 шагов:
шаг 2 вызвал `task(vacancy_assessor)` (субагент сделал score_vacancy + read_work_terms,
вернул structured-вердикт с ловушкой-цитатой), шаг 4 — `task(country_researcher)`
(3 вызова: 2×search_vacancies + read_work_terms, gaps честные). Тайминги узлов:

| узел   |  n | p50, с | p90, с | max, с | комментарии |
|--------|---:|-------:|-------:|-------:|-------------|
| check  |  5 |    0.0 |    0.0 |    0.0 |            |
| plan   |  1 |    8.7 |    8.7 |    8.7 |            |
| replan |  4 |    5.8 |    6.3 |    6.3 |            |
| step   |  5 |    7.9 |   40.3 |   40.3 | шаги с субагентами: 40.3 с (оценщик) и 22.4 с (исследователь), обычные ~7–8 с |

**p90 шага = 40.3 с — порог 60 с (OQ-29) держится**, но шаг с субагентом дороже обычного
в ~5 раз (плюс 2–4 вызова модели субагента внутри `task`). На демо это ок (≤2 task на
шаг, OQ-28); если p90 поползёт к порогу — дроссель на демо-экране уже не спасёт, стоит
считать p90 отдельно для шагов с `task`. Сумма запуска ~135 с (5 шагов, 4 перестройки,
2 субагента).
