# multiplayer

Раздел «Мультиплеер»: совместные игры поверх аккаунтов платформы.
Дружба (код/список) — API `career`, UI в «Аккаунте»; этот домен — только игры/лобби.

Сейчас одна игра: **«Хрюши и Волки»** (Э0–Э15). Каталог следующих идей —
`plans/multiplayer_minigames_2026_08_26.md` (идея №2 «Офферный аукцион» — следующая
вкладка later, не в v1).

## Правила коротко

- **Хрюша (хост)** проверяет бумаги в кабинке, метит улики, ставит штампы:
  НА СОБЕС / ОТКАЗ / НА ПРОВЕРКУ / ОФФЕР.
- **Кандидаты** кладут карты опыта (и блефа), отвечают на вопрос-чип.
- Среди кандидатов спрятаны **волки**. Секреты ролей — только в `state_private`
  своего места; в public — после Reveal.
- Партия = ~5 слотов → Reveal → победа людей / волков / «заморозка».
- **«Ещё раунд»** — тот же стол, новый seed/роли. Каждый новый стол тоже со своим сидом
  (реиграбельность без «стола дня»).
- **Пауза (Dota-стиль).** Любой участник (игрок или зритель) ставит стол на паузу — держится
  бессрочно, таймер фазы заморожен, интенты отклоняются. «Продолжить» жмёт кто угодно →
  `RESUME_COUNTDOWN_S`=3с отсчёт → таймер фазы возвращается на **остаток**, не на полную
  длину. Пауза во время отсчёта отменяет его. Живёт в `session.py` (транспорт), движок про
  неё знает только через `MatchRuntime.paused` — `step()` не начинает новую работу на паузе.
- **Стол с одними ботами закрывается.** Ушёл последний живой (все слоты добиты ботами по
  `_hold_expire_to_bot`), коннектов и hold'ов нет → `drop_if_empty` закрывает стол (и в БД),
  а не держит до idle-GC: ботам между собой играть незачем.

### Лобби (продуктовый контракт)

| Действие | Поведение |
| --- | --- |
| Создать стол | 1 клик → «Стол №N», 2 слота с LLM-ботами, публичный список |
| Войти | свободный/бот → игрок; все люди заняты → зритель |
| Mid-match | зритель садится вместо бота в любой фазе; пустой слот — только BETWEEN |
| Ник | за столом вместо ФИО (`settings.nicks` / @telegram) |
| Слоты | хост `add_slot` до 6 |

Лимиты (Э14): ≤3 open\|playing на хоста; rate-limit create/join; idle GC ~2ч.

## Когда звать LLM

Пять фич и **три модели** (`model_override`, не тир basic). Роли — в `llm.FEATURE_ROLE`,
slug'и — только в `.env`; в Python имени модели нет нигде (Э19.8).

| Фича | Роль / модель | Когда стартует | Fallback |
| --- | --- | --- | --- |
| `wolves_line` | актёр (`MODEL_MULTIPLAYER_ACTOR`) | вход в LINES, **стрим** кадрами `line_delta`, параллельно ≤3 | короткая строка |
| `wolves_bark` | актёр | штамп поставлен — реакция кандидата | «Понял. Пойду дальше…» |
| `wolves_brief` | режиссёр (`MODEL_MULTIPLAYER`) | вход в BULLETIN — сцена дня | «Обычный день кабинета…» |
| `wolves_ticker` | режиссёр | вход в RESULT (принимается и в BETWEEN) | «Слот закрыт…» |
| `wolves_judge` | арбитр (`MODEL_MULTIPLAYER_ARBITER`) | **подача иска в INSPECT** (прогрев) | вердикт движка + молчание судьи |

**Цепочка деградации при `model_override`.** Раньше перегруженный `MODEL_MULTIPLAYER` падал
сразу в глобальный `OPENROUTER_MODEL_FALLBACK` (у нас gemini с обязательным reasoning, +400),
минуя рабочую `MODEL_TIER_BASIC`. С 2026-08-28 `get_chat_model` вставляет модель тира в
цепочку: `override → MODEL_TIER_BASIC → глобальный fallback`. Плюс `OPENROUTER_PROVIDER` в
`.env` (JSON, пусто) — аварийный тумблер provider-routing, если модель rate-limited у одного
провайдера. `MODEL_MULTIPLAYER` увели с `qwen/qwen3.8-flash` (прод-журнал: почти каждый вызов
режиссёра — 429 и/или 17–30 с) на `gpt-5.6-luna`.

Почему так поделено: режиссёру нужна подноготная российского IT, актёру — пластичность
отыгрыша и низкий TTFT (его реплики стримятся в фазу), арбитру — предсказуемый structured
выход. Побочно это разводит нагрузку по трём провайдерам: rate-limit одного не гасит стол.

**Схема — только у судьи.** Остальные отдают одну короткую фразу голым текстом: json_schema
там дороже, даёт свой класс отказов и запрещает стрим. У судьи же есть проверяемое поле —
`cited_marker` сверяется с поданным иском (`wolves_llm._checked_marker`), выдуманная улика
гасится и уходит в WARNING. Вердикт при этом считает `rules.claim_is_correct`, а не модель.

**Не звать LLM:** смена фазы, таймер, раздача ролей, подсчёт очков, штамп без иска,
mid-join, список столов, анимации. Падение OpenRouter не стопает партию — и не меняет её
исход: любой сбой это заглушка в тексте, а не другое решение.

Промпты: `prompts/multiplayer/` (общий канон включается через `{{include:}}`).
Ban-list slop и обрезка — `wolves_llm.sanitize_utterance`.

## Граница «хаб ↔ игра» (Э17)

Домен разрезан надвое. **Generic-слой не знает, во что играют**, и переиспользуется следующей
игрой как есть:

| Generic (под новую игру не трогать) | Wolves-специфика |
| --- | --- |
| `session.py` — комнаты, коннекты, reconnect по seat_token, таймеры фаз, presence, рассылка | `rules.py`, `models.py`, `deck.py`, `views.py` |
| `service.py` / `repo.py` — REST-лобби (create/list/join/close) | `wolves_engine.py` — адаптер под протокол |
| `limits.py` (rate-limit), `gc.py` (idle-GC) | `wolves_llm.py`, `llm.py` — LLM-фичи игры |
| `engine.py` — протокол `GameEngine` + реестр | `prompts/multiplayer/` |

`session.py` ходит в игру **только** через `session.engine`; состояние партии для него
непрозрачно (`GameState = Any`). Обратный доступ — `engine.MatchRuntime`: движок получает
узкий доступ к своей комнате (блокировка, состояние, флаги, broadcast, перевзвод таймера),
чтобы доигрывать за ботов и звать LLM, не возвращая эту логику в хаб. `RoomSession` реализует
этот протокол сам.

Границу стережёт `tests/test_multiplayer_engine_boundary.py`: импорт `rules`/`models`/`deck`/
`views`/`wolves_llm` из `session.py` уронит тесты.

**Чтобы завести вторую игру:** написать её `rules`/`models`/`views`/`deck`, адаптер под
`GameEngine`, зарегистрировать в `engine.get_engine`, выставить `RoomSession.game_id`. Хаб,
лобби, GC и rate-limit не трогать.

**Нон-гол.** Общей машины фаз, общей системы карт/колод и общей библиотеки игровых
UI-компонентов **нет и не строим**. Интерфейс собран из вызовов, которые хаб уже делал, —
не из догадок про будущее. Вторая игра покажет свою форму сама; расширять по факту (Rule of Three).

## Транспорт

- REST: create / list / join / close.
- WS client→server: `ping` | `start` | `sync` | `intent` | `claim_seat` | `host`
  (`kick` | `fill_bot` | `assign_hr` | `add_slot`) | `pause` | `resume`. Клиентский `mid_join`
  в intent запрещён.
- WS server→client: `welcome` | `seat_assigned` | `state` | `line_delta` | `events` | `error`
  | `pong`.
- **Кадр состояния — один конверт (Э20.1).** `{type:"state", rev, lobby, server_now,
  phase_ends_at, pause, public, private?}` — публичная и приватная половины едут вместе, один
  кадр = один рендер. `pause` = `{paused, by, resuming_at?}`. Пара `state_public` /
  `state_private` разобрана на клиенте на переходный период (откат сервера), новый сервер её
  не шлёт.
- **`rev` — монотонный номер кадра (Э20.6).** Клиент отбрасывает кадр не новее применённого
  (после reconnect + `sync` в полёте бывает устаревший). Полный state оставлен как есть:
  на единицах КБ дельта-протокол добавил бы версионирование и риск рассинхрона ради экономии,
  которая не окупается; `rev` в конверте — задел, если дельты когда-нибудь понадобятся.
- **Склейка кадров (Э20.2).** Один клик рождает каскад из 2–3 полных state за миллисекунды
  («интент → боты походили → LLM-фаза»). `broadcast_state` копит их ~20 мс
  (`BROADCAST_COALESCE_S`) и шлёт последний. Стриму реплик ботов не мешает — его кадры идут
  секундами врозь.
- **Прокси-цепочка (Э16).** Апгрейд обслуживает отдельный `location ^~ /api/multiplayer/ws/`
  в `frontend/nginx.conf`: общий `/api/` зачищает `Connection` (это нужно SSE) и не пересылает
  `Upgrade`, из-за чего до FastAPI запрос доезжал обычным GET и получал 404. **Caddy проверен —
  апгрейд пропускает как есть, `deploy/Caddyfile` трогать не надо.** Диагностика цепочки —
  `deploy/ws_probe.sh` (запускать на ВМ; здоровая цепочка = `101` на всех трёх хопах).
- `permessage-deflate` (Э20.7): uvicorn с `[standard]` тянет `websockets`, а тот включает
  сжатие по умолчанию; nginx и Caddy `Sec-WebSocket-Extensions` не режут. На наших пейлоадах
  (единицы КБ) выигрыш косметический — отдельной настройки не заводим.
- `ping` от клиента раз в 25 с — ради направления клиент→сервер (NAT/прокси у игрока). Сам
  uvicorn шлёт свой протокольный ping раз в ~20 с, так что nginx-таймаут держится и без нас.

## Один воркер — несущий инвариант (Э20.5)

`session._HUB` (живые столы, коннекты, таймеры фаз, live-партии) держится **в памяти
процесса**. С `uvicorn --workers > 1` (или `WEB_CONCURRENCY > 1`) комнаты разъедутся по
процессам, и WS-соединение попадёт в воркер, где комнаты нет — стол «то работает, то нет»,
диагностика на день. Горизонтальное масштабирование этой нагрузке не нужно (десяток столов
по ≤6 человек).

- `deploy/Dockerfile` запускает uvicorn без `--workers` (комментарий над `CMD`).
- `api/main.py::_warn_if_multiple_workers` на старте пишет `ERROR` в журнал, если воркеров
  больше одного.
- Стережёт `tests/test_deploy_nginx_ws.py::test_dockerfile_runs_single_uvicorn_worker`.
- Если когда-нибудь понадобится больше — это не флаг, а вынос хаба комнат за пределы процесса
  (Redis/отдельный сервис), отдельный большой разговор.
