# Автоотклики

Автоматизация откликов на hh.ru / getmatch / career.habr.com. Настройки — в веб-разделе
«Расширение» (не «Параметры» — рядом с местом использования, тот же принцип, что у «Мои
поиски» в роадмапе).

## Статус (2026-08-18, Фаза 3 + Фаза 6.1 сделаны; Habr всё ещё нет)

**Владелец, 2026-08-18 (упрощение UI):** активные часы (8.1), лимит на компанию/окно (6.2),

Реализовано (Фаза 3.4, 2026-08-18 — жёсткий гейт подтверждения, owner's spec §3.4):
- **`require_confirmation`** — новое поле `AutoApplyPlatformConfig` (`config.py`), независимое
  от `dry_run`. Редефиниция режима «Тест» на фронте: раньше `enabled+dry_run=true` (тихий
  dry-run, ничего не отправляет), теперь `enabled+dry_run=false+require_confirmation=true` —
  РЕАЛЬНО отправляет, но каждый отклик ждёт подтверждения владельца перед фактическим кликом.
  «Авто» — `dry_run=false+require_confirmation=false`, без подтверждений. Старое
  `dry_run=true` состояние (тихий тест без очереди) больше не достижимо через UI, но
  распознаётся на дисплее как тот же чип «Тест» — никакой автоматической миграции сохранённых
  настроек при деплое, поведение площадки не меняется, пока владелец не тронет переключатель.
- **Общая очередь с анкетой (3.3), не два механизма.** `jobs.anketa`/`AnketaState` теперь несёт
  и анкету (questions непусто), и простое подтверждение письма без анкеты (questions=[]) —
  различаются только этим полем. Раннер (`auto-apply-runner.ts`): первый визит кандидата на
  площадке в режиме «Тест» ведёт себя как dry-run (генерирует письмо, не кликает,
  `effectiveDryRun = dryRun || requireConfirmation`), но исход `dry_run` remapится в
  `needs_confirmation` перед репортом бэку — только тогда бэк паркует очередь
  (`report_attempt` → `_park_pending_confirmation`, без LLM-вызова: письмо уже сохранено
  отдельным вызовом в `jobs.cover_letter_text`, как и раньше при dry-run). Бюджет тика в
  режиме «Тест» — как у dry-run (весь `daily_cap` за тик, не `MAX_REAL_APPLICATIONS_PER_TICK`),
  иначе очередь на подтверждение наполнялась бы по одной вакансии за тик.
- **Резюме-визит (`runAnketaResumeCycle`)** обобщён на оба случая: `AnketaResumeCandidate`
  несёт `letter` (из `jobs.cover_letter_text`, денормализован в `AnketaPendingItem.
  cover_letter_text`) — content-script (`main.ts::runAutoApplyForCurrentPage`) использует его

## Почему DOM, а не официальный API hh.ru

hh.ru закрыл публичный API откликов для сторонних интеграций (owner's call, 2026-08-17) —
вся автоматизация только через расширение, эмулирующее действия залогиненного пользователя
в его собственной вкладке. Реальность `isTrusted`: клик, отправленный контент-скриптом
(`.click()` / `dispatchEvent`), всегда `isTrusted: false` — это гарантия браузера, JS не может
её подделать. Единственный способ получить по-настоящему доверенный клик — `chrome.debugger`
+ CDP (`Input.dispatchMouseEvent`), с постоянным баннером «расширение отлаживает браузер» и
существенно более сложной механикой (виртуальная мышь с траекторией). Это Фаза 3 (эскалация),
если DOM-клик с человекоподобным таймингом (скролл, задержки 1.5–4с, mouseenter/mousedown/
mouseup перед click) не проходит на hh.ru конкретно — сначала должен быть выполнен dry-run +
осторожный ручной тест на реальной вакансии.

## Поверхность обнаружения расширения (чеклист для Фазы 2, owner's spec 2026-08-17)

Отдельно от `isTrusted` (клик) — как сайт вообще ловит присутствие расширения на странице,
до какой-либо автоматизации:

- **Isolated world по умолчанию.** Обычные `content_scripts` (без `"world": "MAIN"`) уже
  живут в отдельном JS-контексте — переменные расширения не видны `Object.keys(window)` со
  стороны сайта. `dock.ts`/`main.ts` этому правилу уже следуют; для hh.ru-автоматизации новый
  код добавлять в MAIN world не нужно (в отличие от `habr-xhr-interceptor.ts` — тому MAIN
  world нужен вынужденно, для чтения `fetch`/XHR страницы, см. ниже).
- **DOM-мусор.** UI панели уже прячется в closed Shadow DOM (`dock.ts:101`,
  `attachShadow({ mode: 'closed' })`) — `element.shadowRoot` возвращает `null` снаружи,
  содержимое не enumerable. CSS панели грузится через `fetch(chrome.runtime.getURL(...))` и
  инлайнится в `<style>` внутри shadow root — `chrome-extension://` URL в light DOM не
  светится вовсе (не `<link href="chrome-extension://...">`). Единственный видимый след в
  light DOM — пустой `<div id="job-hunter-copilot-root">`-хост; для hh.ru новых видимых
  элементов вне этого хоста не добавлять.
- **Monkey patching / `toString()`.** `habr-xhr-interceptor.ts` (MAIN world, только
  career.habr.com — читает `/api/frontend/responses`, ничего не кликает и не шлёт) патчит
  `window.fetch`/`XMLHttpRequest.prototype.{open,send}` — пропатченные функции теперь
  спуфят `Function.prototype.toString` под оригинал (`spoofNativeToString`, добавлено
  2026-08-17), иначе `window.fetch.toString()` тривиально выдаёт подмену. Тот же приём
  обязателен для любого будущего monkey-patch на hh.ru/getmatch, если он появится — сейчас
  для автооткликов не планируется (клик — не патч нативной функции, а вызов чужого
  обработчика через синтетическое событие).
- **`chrome-extension://` в сетевых запросах.** Не грузить картинки/шрифты/скрипты по
  `chrome-extension://<id>/...` НЕ из shadow root / content-script контекста — тот же принцип,
  что уже соблюдён для `panel.css`.
- **Остаточный риск, осознанно принят:** `habr-xhr-interceptor.ts` шлёт
  `window.postMessage({ __jh_habr_responses: true, ... })` и держит буфер-`<script>` в light
  DOM (`__jh_habr_responses__`) — это MAIN↔ISOLATED мост, спрятать некуда (postMessage по
  своей природе публичен на странице). Приоритет ниже, чем hh.ru-клик: только чтение данных
  (не автоматизация действий), только Habr (меньше защиты, чем у hh.ru), уже в проде.

## Принципы (не менять без явного решения владельца)

1. **Выключено по умолчанию на каждой площадке.** Включение — осознанное действие в
   «Расширении», не дефолт продукта.
2. **Пропуск/company-avoid всегда побеждает автоотклик.** `classify_for_auto_apply` не
   принимает флаг «игнорировать скип» — это должно остаться так.
3. **Всё, что не дотянуло до порога, — на ручной разбор, а не молча в мусор.** Порог ровно
   один (2026-09-01): выше — `auto`, ниже — `manual_review`. Полоса `manual_review_band`
   существовала ради этого же, но резала «ниже порога» ещё раз, и вакансии между полосой и
   нулём исчезали без следа, а в UI под это стоял второй ползунок, который никто не понимал.
   Не возвращать: «не показывать вовсе» — решение человека (кнопка «Пропуск», `job.skipped`),
   не порога.
4. **Каждое решение и отправка логируются** (структурные поля через `core.platform.
   observability.event`, не голый `logger.info`) — иначе «итеративно улучшать механизм»
   (owner's spec) невозможно.
