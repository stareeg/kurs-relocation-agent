# Обход блокировки Telegram Bot API (РКН) через Cloudflare Workers

Симптом/причина — `docs/problems.md`, запись 2026-08-05. Коротко: с VM на рос. хостинге
(Selectel) TCP-соединения к `api.telegram.org` глушатся на уровне пакетов (ICMP и весь остальной
интернет при этом работают нормально) — это блокировка на уровне провайдера (РКН), не баг бота и
не баг деплоя. `TELEGRAM_PROXY` (SOCKS5) здесь не помогает: прокси-сервер тоже должен куда-то
достучаться до Telegram, а любой узел в той же российской сети упрётся в то же самое.

Обход — не VPN/прокси-сервер (ещё одна ВМ), а бесплатный edge-воркер Cloudflare, который
перекладывает hostname запроса на `api.telegram.org` и отдаёт ответ как есть. Домены
`*.workers.dev` массово не блокируются РКН (слишком много всего на Cloudflare, чтобы резать всё
подряд). Код бота уже поддерживает подмену базового URL Bot API — `TELEGRAM_API_BASE`
(`bot_app/config.py`, `bot_app/session.py`).

**Для OpenRouter этот же приём не подошёл** (`deploy/render_relay/README.md` — там правильный
фикс): Cloudflare Workers исполняются в датацентре, ближайшем к вызывающей стороне по BGP — с
этой ВМ это стабильно Хельсинки, а именно его блокирует Cloudflare Bot Management самого
OpenRouter (это не РКН, отдельная, более узкая блокировка). Telegram эту проблему не имеет — РКН
не фильтрует IP Cloudflare, поэтому здесь воркер остаётся правильным и рабочим решением. В коде
воркера (`proxy_worker.js`) осталась ветка маршрутизации `/api/` → `openrouter.ai` от первой
попытки чинить обе проблемы одним воркером — она не вредна (просто не используется, `.env`
указывает на неё только для Telegram), трогать/убирать не обязательно.

## Деплой (2 минуты, через дашборд — CLI не нужен)

1. [dash.cloudflare.com](https://dash.cloudflare.com) → завести аккаунт (бесплатно, без карты
   для `workers.dev`-поддомена).
2. **Workers & Pages** → **Create** → **Create Worker** — дать неугадываемое имя (не
   `proxy`/`relay`, что-то со случайным суффиксом — воркер публичный, кто угадает URL, сможет им
   проксировать запросы к Bot API любым чужим токеном; риск невысокий, но задел дёшев) → Deploy
   (дефолтный Hello World).
3. **Edit code** → стереть шаблон, вставить содержимое `deploy/cloudflare/proxy_worker.js` →
   **Save and Deploy**.
4. Скопировать URL воркера (`https://<имя>.<аккаунт>.workers.dev`).
5. Проверить с любой машины:
   ```
   curl https://<url>/bot<TOKEN>/getMe
   ```
   Ожидается `{"ok":true,"result":{...}}`.

## Подключить к боту

На ВМ, в `.env`:
```
TELEGRAM_API_BASE=https://<имя>.<аккаунт>.workers.dev
```
Перезапустить `bot`-сервис:
```
docker compose -f deploy/compose.yaml -f deploy/compose.prod.yaml --env-file .env up -d bot
```
Лог при старте (`bot_app/run.py`): `Telegram API base: https://...` — подтверждает, что
подмена применилась. `docker compose ... logs bot` — polling должен стартовать без `Request
timeout error`.

## Если воркер тоже перестанет открываться

Тот же класс блокировки может со временем накрыть и Cloudflare Workers (провайдеры IP-фильтрации
меняют списки) — тогда пересоздать воркер под новым именем/поддоменом либо перейти на
`TELEGRAM_PROXY` с внешним SOCKS5-узлом вне РФ. Оба пути не требуют менять код бота — только
`.env`.
